# Task for a new session: arms and Inspire-hand object manipulation (simulation first)

Written 2026-11-16 by the simulation session. Use it as the first prompt of a fresh session started in `g1-sim-lab/`.
No hardware is involved: nothing here may publish `rt/lowcmd`, run anything on the robot, edit `robot_deploy/controller*/` or use the `.env` robot credentials. Training and heavy rendering only on the lab desktop (`.env` LAB_*, Tailscale SSH approval from the user each time); the laptop (RTX 3060, 6 GB) is for smoke tests, GUIs and small evaluations.

## Goal
Legs and balance stay with **v11 and v12** (the standard deployed policies). Build a separate **arms-and-hands layer** for object manipulation: first a simulation where the Inspire fingers are commanded properly and objects can be grasped, then the data and interfaces needed to try a vision-language-action policy (GR00T N1.x or pi0.5) for pick-and-place, and to check that v11 keeps the robot upright while the arms work.

## Decisions already taken (do not re-open)
- Arms are NOT part of the leg policies. v11/v12 observe the 14 arm joints and were trained with random arm poses; they do not command them.
- An arms policy must stay inside the arm range v11 handles: `g1_rl/body_env_cfg.py: ARM_POSE_RANGES`, and gentle speeds. Measured (sim, noise on): v11 holds with 0.3-2.2 cm drift while the arms follow human-like reaches (`scripts/evaluate_standing.py` mimic scenarios; the "recommended" band is 60% of the training range around the default pose). Fast or large reaches, and carried loads, are untested.
- SONIC is not the base: it replaces v11/v12 and drives legs and arms together (see the conversation notes: no documented separate-arm mode, unknown waist handling, hand model not stated). It is a reference only.

## What was found (2026-11-16)
- **The finger joints work in Isaac Lab.** The USD (`unitree_sim_isaaclab/assets/robots/g1-29dof_wholebody_inspire/g1_29dof_with_inspire_rev_1_0.usd`) has 12 independent revolute finger joints per hand (24 total), each with a drive, no mimic coupling:
  `{L,R}_{index,middle,ring,pinky}_{proximal,intermediate}_joint` (limits 0..1.70 rad) and `{L,R}_thumb_{proximal_yaw (-0.1..1.30), proximal_pitch (-0.1..0.60), intermediate (0..0.80), distal (0..1.20)}_joint`.
  In our V11 Play environment all 24 followed position targets to within 0.01 rad (open and 80% closed). They looked frozen because nothing commands them: the events hold them at default (`ev.hold_joints`, pattern `^[LR]_.*`, targets set at reset), there is no hand action term, and the GUIs have arm sliders only.
- **Our hand actuator** (`g1_rl/robot_cfg.py`, copied from Unitree's sim): implicit PD, stiffness 1000, damping 15, effort limit 100, armature 0. The USD drives themselves say stiffness 1.745 per degree (about 100/rad) and max force 12 N*m (thumb 30). These are strong and unvalidated for grasping.
- **The real Inspire hand has 6 motors per hand**, not 12 joints: little, ring, middle, index, thumb bend, thumb rotation. Unitree's sim already maps 6 commands to the 12 joints (`unitree_sim_isaaclab/action_provider/action_provider_dds.py`, `inspire_hand_joint_mapping` and `special_joint_mapping`): each `*_intermediate_joint` copies its finger's proximal target (ratio 1.0); `thumb_intermediate` = 1.5 x thumb pitch; `thumb_distal` = 2.4 x thumb pitch.
  On the robot the hands are a separate system: Modbus TCP, left 192.168.123.210, right .211, port 6000, angle registers 0..1000 per finger (see `UnitreeRobot/g1_gui/hardware_controller.py`: `ADDR_ANGLE_SET` 1486, speed 1522, force 1498, actual angle 1546, order little, ring, middle, index, thumb_bend, thumb_rotation).
- **Unitree's sim has ready manipulation tasks for G1 + Inspire** (not run by us yet): `pick_place_cylinder_g1_29dof_inspire`, `pick_place_redblock_g1_29dof_inspire`, `stack_rgyblock_g1_29dof_inspire`, `move_cylinder_g1_29dof_inspire_wholebody` in `unitree_sim_isaaclab/tasks/g1_tasks/`, with cameras, objects, a DDS interface, and teleoperation/replay providers. They use Unitree's own leg handling, not v11.
- **Arm joints on the robot**: motors 15-21 left, 22-28 right (shoulder pitch, roll, yaw, elbow, wrist roll, pitch, yaw). Limits in `UnitreeRobot/g1_gui/hardware_controller.py` (`JOINT_LIMITS`). Onboard gains seen: shoulders and elbow kp 60 / kd 3, wrists 40 / 3; the old arm GUI used kp 50, kd 1 and a 0.4 rad/s ramp.
- **VLA requirements** (from the repos' docs, verify before spending): GR00T N1.6/N1.7 (3B, embodiment tag `UNITREE_G1`, LeRobot-format demos, at least 50-100 demonstrations suggested, fine-tuning about 20,000 steps on a multi-GPU machine, inference on 16 GB+); pi0.5 (`openpi`: inference 8 GB+, LoRA fine-tuning 22.5 GB+, full fine-tuning 70 GB+). The lab GPU is an RTX A4000 16 GB: inference only, no fine-tuning. NVIDIA's GR00T workflow outputs SONIC latents (whole body); an arms-only use needs the decoupled variant (RL legs + IK arms) or a custom embodiment config.
- **Important interface fact**: on the robot only ONE process may publish `rt/lowcmd`. v11's controller (`robot_deploy/controller/run.py`) publishes all 29 joints, arms included (it holds them at the default pose). So an arms policy cannot be a second publisher: its targets must enter the leg controller as an input stream (clamped, rate-limited), or the controller must be extended. That is a design item for the hardware session, written as a task note (see Step 6), not something to code in `controller/`.

## Steps
1. **Hand module and finger sliders (laptop).**
   - `g1_rl/hands.py`: pure functions (torch and numpy) from 6 normalised commands per hand (0 = open, 1 = closed, in the real hand's finger order little, ring, middle, index, thumb bend, thumb rotation) to the 12 joint targets per hand using the limits above and the coupling ratios; the inverse for logging; unit tests (no Isaac): limits respected, monotonic, coupling ratios exact, left/right symmetry, round trip. Check the direction of each command against the real hand's 0..1000 meaning with the user before fixing the convention.
   - Add finger sliders (6 per hand) and a "close / open hand" preset to `scripts/play_arms.py` (the arm GUI) and drive the hand joints from them, keeping v10/v11 standing. Smoke test on the laptop, then show the user.
   - Hand actuator gains: check how the hands behave at the current gains with a grasp (Step 3) before changing them.
2. **Look at Unitree's Inspire tasks (lab GPU, rendering).** Run `pick_place_cylinder_g1_29dof_inspire` headless on the lab; record a video, list the observations (cameras, joint states), the action space and the object definitions; note what it uses for the legs. Report what can be reused (scene, objects, cameras, replay/teleop) and what depends on Unitree's stack.
3. **Grasp quality.** In whichever environment fits (ours with a table and an object added, or Unitree's task): grasp a cylinder and a box with each hand; tune finger gains/effort, friction of the fingertip and object materials, collision approximations; report slip, crushing and thrown objects. Keep the changes in config, not in the USD.
4. **Balance with manipulation motions (lab).** Replay pick-and-place arm trajectories (from Step 2, or hand-built reach-grasp-lift-place) while v11 holds: drift, tilt, foot lifts, falls, with observation noise, with a carried object of 0.5-2 kg on one hand, and with the arm speeds the VLA would use. Extend `scripts/evaluate_standing.py` for this; compare with the mimic scenarios. If v11 falls or steps: report the speed/range/load limits to impose on the arms layer; only then think of a v11 retrain with manipulation motions.
5. **VLA fit.** With the findings, write a short decision note: GR00T (with which embodiment, decoupled legs) vs pi0.5, the data format needed, how demonstrations would be collected (teleoperation in sim and/or on the robot), GPU needs and where each step runs, and the smallest end-to-end experiment (one object, one task, 50 demonstrations). Do not start collecting or training before the user decides.
6. **Hand-off for the hardware side.** A note in `robot_deploy/docs/` for the hardware session: the arm-target input into the leg controller (message format, 50 Hz, clamp to `ARM_POSE_RANGES`, rate limit, how it interacts with the stop sequence), the Inspire hands on Modbus (separate from `rt/lowcmd`), and the camera feed (the hardware console in `robot_deploy/gui/` already shows the RealSense; the topic is `/camera/camera/color/image_raw`). Code in `robot_deploy/controller*` stays theirs.
